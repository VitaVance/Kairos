# Contract：ADR 0004 §4 在 packages/ 的落地

> 这是派发前冻结的边界定义。**改它需要先改这份文件，不能各自在实现里决定。**

## 问题

`core/domain/task.ts:6` 的 `quadrantOf` 只看两个用户布尔值：

```ts
if (task.important && task.urgent) return 'urgent-important';
```

`isOverdue()` 存在、有完整测试（`core/test/scheduling.test.ts:76-92`），
但 `packages/features/src` 与 `apps/desktop/src` 里**零调用者**。

于是产品里的事实是：**一件事过期三个月，仍然不是紧急的，不会进 Q1，
除非用户自己想起来去勾那个勾。**

ADR 0004 §4 写的是：

```
紧急 ≡ 用户标了紧急  或  时间把它推过了紧急线
```

这一行在数据层从未实现。

## 决策 1：紧急是派生的，重要是用户说的

- `important` —— 仍然只是一个用户布尔值。系统从不替用户决定轻重。
- `urgent` —— 用户**可以**标，但**时间可以把它推上去，用户不能把它压下来**。

因此 `quadrantOf` 需要一个时钟：

```ts
export function quadrantOf(
  task: Pick<Task, 'important' | 'urgent'>,
  now?: Instant,
): Quadrant
```

**`now` 缺省时退回纯用户口径。** 这不是为了兼容，是因为三个调用点里有两个
（拖拽判定、列表筛选）问的是「用户把它放在哪」，不是「它现在算什么」。

## 决策 2：只有「已过期」才进 Q1

分级（沿用 `data.js` 已用 16 条断言验证过的阶梯）：

| 级 | 何时 | 进 Q1 |
| --- | --- | --- |
| `none` | > 14 天 / 无日期 | 否 |
| `far` | 14 天 ~ 3 天 | 否 |
| `soon` | 3 天 ~ 24 小时 | 否 |
| `near` | 24 小时内 | **否** |
| `urgent` | 已过期 | **是** |

`near` 不进 Q1 是刻意的：**艾森豪威尔矩阵的本意是让 Q1 保持小。**
如果 24 小时内就进 Q1，Q1 会长期拥挤，矩阵退化成「按日期排序的列表」。

代价：明天的事在板上仍是 Q2，过期才变红。补偿是行上**必须**显示
「明天到期」+ `--tl-warning-ink`。**信号放在行上，不靠移动卡片。**

## 决策 3：拖出 Q1 的语义（**ADR 0004 未解决的那一处**）

如果过期的事自动算紧急，那么把一件过期的事拖到 Q2 会发生什么？
它仍然是过期的，所以仍然在 Q1 —— **拖动看起来失败了。**

这是真实矛盾，不是实现细节。三个选项：

| 选项 | 结果 | 判定 |
| --- | --- | --- |
| A. 时钟赢，拖动无效 | 用户拖了没反应 | 坏：一个不响应的控件 |
| B. 拖动清掉 `urgent`，但它仍在 Q1 | 拖动"成功"了却看起来没成功 | 更坏：撒谎 |
| **C. 时钟赢，拖动被拒绝并说明原因** | 「这件事已经过期，只能完成或改期」 | **采纳** |

**采纳 C。** 理由：你**不能**声明一件已经过期的事"不紧急"——
这和管理学上的常识一致，也是 ADR 0004 §4「用户不能压低时间」的直接推论。
用户能做的只有两件事：**做掉它，或者给它一个新日期**。

所以：
- 拖拽一件**因时间而进 Q1** 的任务到其它象限 → 拒绝，`aria-live` 播报
  「已过期的事不能移到别的象限，只能完成或改期」。
- 拖拽一件**因用户标记而进 Q1** 的任务 → 允许（清掉 `urgent`），
  因为它没有过期，用户的判断是最高权威。
- 拖拽非 Q1 的任务进 Q1 → 允许（设 `urgent: true`）。

判定「是否因时间而进 Q1」的唯一函数：`isOverdueNow(task, now) && !task.urgent`。

## 决策 4：「现在」从哪里来

`packages/core` 不含全局时钟。已有一个 `clock` 依赖（`TaskServiceDeps`）。

- **领域函数**（`quadrantOf`、`isOverdue`）只接收 `now: Instant` 参数，不读全局。
- **UI** 需要一个会走的时钟。`features/calendar/DayView.tsx:80` 已有
  `useNowMinutes(active)`，每 60 秒 tick。**把它提到共用位置**，不要在
  四象限板里写第二份。

  > 这是本契约里唯一允许的跨文件移动。新位置：`features/src/shared/useNow.ts`。
  > DayView 改为从这里 import，行为不变。

## 决策 5：行上必须显示的三件事

否则矩阵是个静态分类表。每一行：

1. **结束时间**（当 `dueAt` 有结束值，或 `allDay` 且跨天）
2. **时间读数**：`near` → 「今天到期」/「明天到期」；`urgent` → 「已过期」
3. **为什么在 Q1**：时间推上去的 → 「已过期」；用户标的 → 「你标的紧急」

第 3 条是关键：**用户必须能区分「我决定的」和「时间决定的」**。

## 不允许做的事

- **不改存储。** `important` / `urgent` 两个布尔不变。没有新字段。
- **不改 `isOverdue` 的判定。** 它的 16 条测试是这一版的地基。
- **不在 UI 层重算象限。** 所有视图调同一个 `quadrantOf(task, now)`。
- **不给 `near` 加第四条象限。** ADR 已经否决过。
- **不改 `compareTasks` 的主要排序。** 「粗窗口在前」是 ADR 0004 的独立决策。

## 验收

1. `core` 单测：`quadrantOf(task, now)` 对五级读数各自的归位；`now` 缺省时退回纯用户口径。
2. 一条过期但 `important:false, urgent:false` 的任务 → 出现在 `urgent-not-important`。
3. 一条明天到期、`important:true` 的任务 → 仍在 `not-urgent-important`，但行上有「明天到期」。
4. 拖拽被拒绝时 `aria-live` 有播报。
5. `pnpm test` / `pnpm typecheck` / `pnpm lint` 全绿。
6. 真实应用截图：Q1 里同时有「用户标的」和「时间推的」，两者标记不同。
