# ADR 0004：一个概念、一条时间阶梯、紧急由用户说

- 状态：已接受
- 日期：2026-11-26
- 取代：G 稿（`design/G-capture-bar.html`）的「任务/日程」类型开关

## 背景

用户的三句话定义了整件事：

> 「任务 / 日程，你引入了这两个概念，但是在四象限和各个日历视图里完全区分不出来啊。
> 别硬造概念，都是要干的事。只是有的是有明确时间，有的只是有个大概时间甚至没有时间限制。」
>
> 「产品设计一定要逻辑全局一致，这本质上是管理学的问题。」
>
> 「我觉得不要让用户去理解 任务 / 日程 的区别」

现状：两种记录（`tasks` / `events`）、两套生命周期、两套能力。审计
（`docs/CONCEPT-AUDIT.md`）找出 4 个 P0、12 个 P1，其中六项能力里有四项只属于其中一种：

| 能力 | 任务 | 日程 |
| --- | --- | --- |
| 勾完成 | ✓ | ✗ |
| 重复 | ✓ | ✗ |
| 进四象限 | ✓ | ✗ |
| 被搜索到 | ✓ | ✗ |
| 进日历 | 有日期才进 | 恒进 |
| 提醒 | ✓ | ✓（唯一已合并的层） |

同一件现实里的事（「每周五复盘」），能不能重复、能不能勾掉，取决于用户当初点了哪张表。
这不是设计取舍，是两套模型各长了一半。

## 决策

**一个用户概念，按「时间说到多细」分档；「紧急」由用户声明，时间只负责把它读出来。**

### 1. 一个概念

用户可见的只有「一件事」。没有任务/日程之分，捕获时不选类型，详情面板只有一个，
日历上点开任何一格都是同一个地方。存储层面的合并见 ADR 0005（待写）。

### 2. 四个词，五种形状（v2 · 依据用户两次修正重写）

v1 写的是「六档精度」（none/month/week/day/period/time）。那是错的，而且错在两处：
**把用户概念和存储形状混为一谈**，以及**把「这周」当成一个时间点**。

用户的两句话定了形：

> 「有的是有明确时间，有的只是有个大概时间甚至没有时间限制。比如开会是明确时间，
> 平时工作可能只会具体到天或者半天，有些任务比较大，只能说是这周或者下个月这种，
> 或者完全不做限制」
>
> 「我觉得当我说这周这个月时，没必要放在日历上每一天吧，这样太不友好了」

**用户只需要记四个词。** 存储有五种形状，但其中两种是同一个词的预设。

| 用户说的词 | 形状 | 存储 | 举例 |
| --- | --- | --- | --- |
| **不限** | 无日期 | 无 | 整理浏览器书签 |
| **某天** | 一天 | `start_at` = 当天，`end_at` = 次日 0 点，`all_day` | 交房租（周六） |
| （某天的细分）| 半天 | 同上 + `due_period` | 回客户邮件（今天下午） |
| **几点** | 一个时刻，可选结束 | `start_at` + 可选 `end_at` | 产品评审会 15:00–16:00 |
| **一段时间** | 一段有起止的日期 | `start_at` / `end_at`，`all_day` | 出差 12/3–12/5 |

**「这周」「下个月」不是第五、第六个词，是「一段时间」的预设。**
选中它们时，写入的就是那一段的真实起止日期（本周 = 本周一 → 下周一；本月 = 1 号 → 次月 1 号）。
用户看到的是「这周」，数据库里存的是一个区间。这解决了 v1 最根本的毛病：

> v1 把「这周」当成一个**精度档**（一个点），于是为了让它在日历上看得见，
> 只好把它复制到七个格子里——那正是用户说的「太不友好」。
> 把它当成**区间**，它在日历上自然就是一条横跨那几天的带。一个字都不用复制。

### 区间在日历上怎么画

| 视图 | 「一段时间」的画法 |
| --- | --- |
| 月视图 | 一条横带，横跨它真正覆盖的那几天；跨周时按周切段，续段不加圆角、不带前导竖条 |
| 周视图 | 同上，在网格上方的全天带里横跨 |
| 日视图 | 顶部一条「本周/本月」区，因为它不属于某一个时刻 |
| 年视图 | 该月卡片上的一行小字，不进日格 |

**关键：横带只横跨它真正覆盖的列。** 一个 11/23–11/29 的区间横跨那七列是对的；
一个「下个月」横跨 12 月整月也是对的。这与「同一件事出现七次」的区别在于——
横带是**一个连续的形状**，用户看到的是「一件事占了一段」，而不是「七件一样的事」。

### 会过期吗

| 形状 | 过期判定 |
| --- | --- |
| **一段时间** | **否**。区间过去了不等于迟到了，它是计划窗口。窗口过了显示「上周·未完成」，用 `--warning-ink` |
| 某天 / 半天 / 几点 | 是。按精度各自的边界判定，用 `--danger-ink` |

理由：一段时间表达的是**计划**（「我打算这周弄」），不是**承诺**（「我保证周三前交」）。
把计划窗口当截止日，周三一过它就变红——而用户从没承诺过周三。这也是审计 §4.9 那个 bug 的另一面。

**被否决的两个形状：**

- **「以后 / Someday」单独成为一个词。** 它的行为与「不限」完全相同（不进日历、不过期、不提醒）。
  给它一个独立的词，等于让用户在两个没有区别的选项之间做一次无意义的选择——
  正是用户说的「别硬造概念」。真要分开，那是一个**清单**（叫「以后」），不是一种精度。
- **「这周」「本月」各自成为一个词。** 同一个形状、两种预设宽度。存两个答案问「窗口多长」，
  迟早会不一致。

### 3. 一段时间的滚动规则

这是产品最容易被做成「永远不做」的地方，必须钉死：

- 「这周」写入的是**那一段的真实起止**（本周一 → 下周一），不是浮动的引用。
- 区间结束之后、仍未完成：
  - 在列表里显示为 **「上周」** + 一个 `未完成` 标记（`--tl-warning-ink`）；
  - **不自动跳进本周**。自动跳 = 用户永远看不到自己拖了多久。
- 用户点一下「顺延到本周」，起止日期才移动。**移动是一次真实的选择**，并记入撤销栈。
- 「下个月」同理：区间过去后显示「上个月·未完成」。

这条的选择是：**宁可让用户看见自己拖延，也不替他把日期往后抹。** 一个会自己滚动的
「这周」等于一个永远不会失败的承诺，而矩阵的价值恰恰来自「什么没做完」这件事看得见。

### 4. 紧急：用户说了算，时间只读

```
紧急 ≡ 用户标了紧急  或  时间把它推过了紧急线
```

- 用户永远可以标紧急，**包括没有日期的事**（「老板刚发的」）。
- 用户**不能压低时间**：明天到期的事不能说它不急。想让它不急，把日期推远——
  那是一个留下痕迹的决定。
- 时间侧的读数 `urgencyOf(item, now)` 是五级纯函数，已在
  `scripts/urgency.mjs` 用 16 条断言验证（单调、无跳变、每级可达）：

| 级 | 何时 | 进四象限的「紧急」列 |
| --- | --- | --- |
| `none` | > 14 天 | 否 |
| `far` | 14 天 ~ 3 天 | 否 |
| `soon` | 3 天 ~ 24 小时 | 否 |
| `near` | 24 小时内 | **否** |
| `urgent` | 已过期 | **是** |

**`week` / `month` 两档不参与这个阶梯的「过期」判定。** 它们的窗口过去了，读数停在
`far`，进 Q1 的唯一途径是**用户手标紧急**。理由与 §2 一致：计划窗口不是截止承诺，
窗口过去不等于「迟到了」。它们在行上改用 `--tl-warning-ink` + 「上周·未完成」表达
「窗口已过」，走的是 §3 的滚动规则，不是逾期规则。

这条是实施时才发现的坑：按剩余小时数硬算的话，一条上周的 `week` 会算出负数 → `urgent`
→ 自己跳进 Q1，与「week 不算逾期」直接矛盾。

`near` 不进紧急列，是刻意的：**艾森豪威尔矩阵的本意是让 Q1 保持小**。
如果 24 小时内就进 Q1，Q1 会长期拥挤，矩阵退化成「按日期排序的列表」。
熵增的代价比「晚一步」更大。

代价是：明天的事在板上仍是 Q2，过期才变红。为补偿，`near` 的行**必须**显示
「明天到期」的措辞 + `--tl-warning-ink`，让用户在板上不靠象限也能看出紧迫。
**信号放在行上，而不是靠移动卡片。** ——卡片移动会让人以为「这是另一件事了」。

### 5. 完成之后：留在清单，离开日历

- 勾掉之后，条目**留在四象限板**，折叠进「已完成」（现有行为，保留）。
- 勾掉之后，条目**离开日历**。理由：日历记的是**安排**，清单记的是**完成**。
  已完成的块留在时间轴上会让日历变成一份越来越挤的历史，而用户看日历是为了看
  接下来要做什么。
- **年视图热力图改为「发生过的事」口径**，与月历一致：
  计数 = 当天**未完成的安排** + 当天**已完成的事**。
  已完成的照样计数，因为热力图问的是「这天你忙不忙」，不是「这天还剩什么」。
  这样月历（只看未来）与热力图（看密度）各答各的问题，不再互相矛盾。

  现在的实现是：`heatByDay()`（`calendar/year-math.ts:104-117`）对传入的每条无差别计数，
  而 `data` 来自 `CalendarService.entriesBetween()`，含已完成——所以热力图数的是
  「安排了多少」，不是「干了多少」。

  **改法必须是一个数据源、两个消费者各筛各的**，不能让渲染层过滤后再喂给热力图——
  那样已完成的条目会被筛掉，热力图就数不到了（这是本稿 v1 写反的地方）：
  - `entriesBetween()` **不变**，返回全集（含 `done: true`）；
  - 月视图 / 周视图 / 日视图的网格渲染**在渲染时跳过** `done === true`；
  - 年视图的 `heatByDay()` **不过滤**，照旧全量计数。
  两处口径由同一个字段派生出两个**不同的问题**，不是一个开关，也不是一条被过滤过的数组。

代价说清楚：用户没法在月历上回顾「这周我干了什么」。补偿是四象限板的「已完成」折叠，
与热力图（它记的正是「哪天忙过」）。**不为此新增一个「显示已完成」开关**——
那是把设计问题推给用户。

### 6. 「过去的事」不会自动完成

昨天开完的会、上周的评审，勾不勾由用户决定，系统不猜。
理由是「开完了」不等于「这件事结束了」：会议开完还要写纪要。
但**已过期的 `time` 条目必须有视觉信号**（`--tl-danger-ink` 的时间 + 「已过」），
否则板上会堆一批看不出状态的过去事件。

## 后果

**变好**

- 捕获时不选类型：少一个决定，少一个能选错的地方。
- 「这周」「下个月」可以说出来，不必编一个假日期。精度不再被迫高于事实。
- 四项只属于一种的能力（完成、重复、象限、搜索）对所有事一视同仁。
- 提醒层的 `reminderAnchorOf` 终于能覆盖一切，全天日程不再永不提醒（审计 §4.2）。

**代价**

- 存储迁移：两张表合一，真实数据 18 条任务 + 13 条事件需迁移。
- 「一段时间」是**新的形状**：现有代码只有「一个点」（dueAt）和「一天」（dueDate），
  没有任何一处表达「一段有起止的日期」。这是本次改动里工作量最大的一块。
- 年视图热力口径要跟着改，否则同一个月历两个说法。
- 「已完成离开日历」与「板上一眼看到这周干了什么」之间有张力，本 ADR 选择站在日历一边。

## 每一种形状在行上的样子

傻瓜逻辑的检验标准是「不看说明也能懂」。因此每种形状在**行上说什么、排在哪、什么颜色**
必须一次定死，不能留给实现时随手决定。

| 形状 | 行上的文字 | 排序位置 | 文字颜色 | 例句 |
| --- | --- | --- | --- | --- |
| 一段时间（本月） | 「下个月」 / 「2027年1月」 | 第 1（最前） | `--tl-text-secondary` | 更新简历 |
| 一段时间（本周） | 「这周」 / 「上周·未完成」 | 第 2 | `--tl-text-secondary`；逾期用 `--tl-warning-ink` | 写季度总结 |
| 一段时间（任意起止） | 「12/3 – 12/5」 | 第 3 | 同上 | 出差 |
| 某天 | 「周五」 / 「今天」 | 第 4 | `--tl-text-secondary`；逾期用 `--tl-danger-ink` | 交房租 |
| 半天 | 「周五下午」 | 第 5 | 同上 | 回客户邮件 |
| 几点 | 「周五 14:00」 | 第 6 | 同上 | 产品评审会 |
| 不限 | 清单名（如「收集箱」） | 最后 | `--ink-quiet` | 未排期：随手记 |

「下个月」不带具体日子，「12/3 – 12/5」带——两者在行上必须肉眼可分，否则用户会以为
自己当初填了具体日期。这条靠措辞保证：**预设的窗口只显示窗口名，不显示它落在哪几天**。

排序规则一句话：**粗窗口排在细窗口之前**——「下个月」→「这周」→「某段起止」→「周五」→
「周五下午」→「周五 14:00」→「不限」。同一形状内按起始日期升序。

> 注意 `--ink-quiet` 而不是 `--tl-text-tertiary`：后者在浅色画布上实测 4.27–4.33，
> 低于 4.5。「不限」是行上唯一会跟清单名混在一起的信息，必须读得清。

为什么反过来（粗在前）：一个「下个月」的条目如果排在「周五 14:00」后面，用户要先
扫过所有精确的事才能看见它；而粗窗口的事恰恰是最容易被忘、最需要被看见的。
精确的事自己有时间点会提醒，粗窗口的事没有提醒——**排前面是它唯一的保险**。

这条取代现有的 `compareTasks`（`domain/task.ts:121-133`，按 `dueAt` 升序）。
它对 `week`/`month` 会得到同一个周一/月首的时间戳，于是「下个月」和「下个月 1 号」
排在相邻位置、看不出差别，而且「下个月」会排到「今天」后面。

连带影响：`compareTasks` 同时负责「未完成在前」。这条保留不变。

## 被否决的方案

1. **只统一界面，不动存储。** 用户不用学区别了，但「为什么这条不能勾完成」会一直存在，
   要靠 UI 抹平结构差异。用户选了更彻底的一条。
2. **紧急完全派生。** 无日期的事永远进不了 Q1，而「老板刚发的」正是最常见的一类。
3. **紧急完全手动。** 两个时钟继续打架，审计 §4.9 的病根没除。
4. **`week` 自动滚动。** 一个永远不失败的承诺，看不见拖延。
5. **`near` 进 Q1。** Q1 长期拥挤，矩阵退化。
6. **已完成留在日历。** 日历变历史，且与年视图口径继续分叉。
7. **`week` / `month` 在网格里按天重复出现。** 这是本 ADR v1 自己的规则，被用户否掉：
   「没必要放在日历上每一天吧，这样太不友好了」。同一件事在七个格子各出现一次，
   读起来像七件事；而且它把一个没有时间点的东西钉在了每一天上，制造虚假的精确。
   改为「顶部一条带」，见 §2。
8. **`week` / `month` 完全不进日历。** 那样用户切到日历就彻底看不见本周该做什么，
   等于把「计划」和「日历」割裂。带是折中：一处出现，但每个日历视图里都在。
