# ADR 0006：区间不是日历条目

- 状态：已接受
- 日期：2026-11-27
- 取代：ADR 0004 §2「区间在日历上怎么画」的整张表，以及被否决方案 #8 的折中结论
- 相关：ADR 0004 §3（区间不自动滚动）、ADR 0005（存储合并，待写）

## 背景

ADR 0004 §2 规定「一段时间」在日历上是**一条横跨它覆盖那几天的连续横带**，
理由是「眼睛读到的是这件事占了一段」。

用户看过 v2 设计稿后的原话：

> 「在日历里，出现一个任务横跨多天的长条还是有些抽象。传统上应该是甘特图吧，
> 日历一般是放精确到小时分钟的吧」

诊断成立，而且比「抽象」更具体。

### 一根条子没有量

甘特图里条的长度 = 工期，**长度本身就是信息**。日历的列宽被日期切分固定，
所以每根区间条都一样长，不管那件事是一小时还是一周。实测这一版的 5 条区间：

| 事项 | 档 | 画出来的跨度 | 真实工作量 |
| --- | --- | --- | --- |
| 更新简历 | 月 | 12/1 → 12/31（31 天） | 一个下午 |
| 年度体检 | 月 | 12/1 → 12/31（31 天） | 一小时 |
| 写季度总结 | 周 | 11/23 → 11/30（7 天） | 几小时 |
| 部门聚餐筹备 | 周 | 11/23 → 11/30（7 天） | 几小时 |

「更新简历」和「年度体检」在月历上画出来**像素级相同**（`design/v2/03-calendar-month.html`，
截图 `uv-03-dec.png`）。**一根所有条都等长的柱状图不是图，是装饰。**

### 两种区间被画成了同一种

- **占用（occupancy）**：这段时间已经被拿走了——出差、会议、假期。
  它**是**一个时间事实，条是诚实的。
- **意图（intention）**：我想在这段时间里做这件事——写完季度总结。
  条在这里是**虚假的**：它宣称这一段被占满，而用户只说过「我想这周弄完」。

ADR 0004 把两者画成同一根条。这是「抽象」的根源，不是颜色或圆角的问题。

### 产品自己已经给出了正确的语法

`design/v2/05-agenda.html` 把「写季度总结」画成**一行 + 「11/23 → 11/30」**，
没有条。`13-year.html` 在月卡里写一行字，也不画条。**五个视图里两个已经避开了。**

所以那根条不是必然，是三个网格视图各自选的。

## 决策

**区间不是日历条目。它只在真正占用时间时才有资格进入日格。**

### 1. 分界线

```
占用（occupancy）  → 可以画在日格上，条的长度就是占用长度
意图（intention）  → 不进日格。它属于「该做什么」，不属于「什么时候」
```

判断标准是**用户有没有承诺一段时间**，不是这件事重不重要。
「出差 12/3–12/5」是承诺（那三天人不在）；「写完季度总结，这周」不是。

### 2. 每个视图怎么画

| 视图 | 意图（这周 / 下个月 / 本周内任意起止） | 占用（跨天且已承诺） |
| --- | --- | --- |
| 月视图 | **周界上的一个计数**（`第 48 周 · 2`），不是条 | 一条横带，横跨真正的天数 |
| 周视图 | **全天行里的一个芯片**，写「这周 · 2 件」，点开展开当日该做的 | 一条横带 |
| 多日视图 | 同周视图 | 一条横带 |
| 日视图 | 顶部「本周窗口」区，一行文字 | 全天行里的横带 |
| 日程视图 | 一行 + 日期区间（**现状，不动**） | 一行 + 日期区间 |
| 年视图 | 月卡里一行文字（**现状，不动**） | 同左 |

**关键：计数的语法已经在产品里了。** 月视图 26 号格子上的「+3」就是同一个族——
「这一天还有 3 件没显示」。区间用它自己的版本：「这一周有 2 件窗口内的事」。
一个计数一个字形，比一根等长的条诚实得多，因为它**不假装自己量了什么**。

### 3. 为什么不做甘特图

甘特图的价值全在**依赖关系、关键路径、资源平衡**。这个产品一样都没有，
也不该有——给个人待办做甘特，等于把项目管理工具的核心概念搬进来，
正是用户说的「别硬造概念」。

**但用户对甘特图的直觉是对的**：长度只有在轴变粗时才有意义。
如果将来要看「这周扛了多少」，正确的做法是做一个**以周或月为轴的时间线**
——轴的单位从「天」变成「周」，条的长度才有含义。那是**另一个视图**，不是日格。

## 后果

**变好**

- 日格重新只回答「什么时候」，这正是用户对日历的期待。
- 所有条都等长这个失效的编码消失了。
- 月视图每一行少两根跨格长条，格子里的真实安排（几点、半天）重新成为视觉主体。
- 与日程视图、年视图的语法统一：**五个视图对同一件事说同一句话**。

**代价**

- 「这周要做什么」在月视图上不再一眼可见，要读一个计数。
  补偿：四象限板和清单里它排在最前（ADR 0004 §「粗窗口在前」），
  而那正是用户决定「该做哪个」的地方。
- 需要区分占用与意图——目前的数据模型里两者都是 `start_at`/`end_at`。
  **ADR 0005 必须加一个字段**（暂名 `blocks_time`），否则渲染层无从判断。
  这是本 ADR 对存储层的唯一要求。

**被否决**

1. **保留横带，只改样式**（变细、变淡、加斜纹）。长度仍然没有量，问题不变。
2. **做成真甘特图**（可拖拽调整起止、画依赖）。见 §3：产品没有那个需求，
   而拖拽调整起止会把「说个大概」重新变成「排一个精确计划」。
3. **区间完全不进日历**（ADR 0004 被否决方案 #8 的彻底版）。
   那样用户切到日历就看不见本周还有什么窗口内的事，计划与日历割裂。
   计数是折中：**出现，但不占据任何一天。**
4. **按周分泳道**（像多日视图那样一行一个区间）。仍然是等长条，仍然是装饰。

## 与 ADR 0004 的关系

本 ADR **只推翻 §2 的渲染规则**，不推翻 §1（一个概念）、§3（不自动滚动）、
§4（紧急五级）、§5（完成离开日历）、§6（过去的事不自动完成）。

§2 的**「四个词、五种形状」本身仍然成立**——区间是一个真实的形状。
改变的是：**它不在日格上有一个形状。** 形状活在行上、在日程视图里、在计数里。
