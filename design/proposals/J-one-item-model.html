一个事项模型 · 设计提案 J v1

任务 / 日程，你引入了这两个概念，但是在四象限和各个日历视图里完全区分不出来啊。 别硬造概念，都是要干的事。 ——这句话是对的，而且它指向的不是一个控件，是数据模型。 本稿的答案是删掉一个概念：两张表合成一张，捕获条上的类型开关删除， 点开任何一块都进同一个详情面板。「任务 / 日程」的区别对用户完全不可见。

依据：schema.ts:36/51（两张表）、types.ts:176（CalendarEntry 早已统一）、 calendar.ts:52（无日期不上日历）、Shell.tsx:429-432（唯一的点击分叉）、 list-service.ts:54（清单删除守卫）、migrate()（无事务）。

上面两条是两个不同的对象：一条 Task、一条 CalendarEvent。 在日历上它们逐像素相同：同色、同时段、同标题。点开才发现一个进任务面板、一个进日程编辑器 （Shell.tsx:430）。

  • 用户不是「分不清」，是没有东西可分。日历只投影 CalendarEntry， 而 types.ts:176 的注释自己写着「the calendar never needs to know which source an entry came from」。视图层早就不分了，是模型在强迫两个编辑器分。
  • 第三条 chip 是一个读数。「15:30 接孩子」在存储里是一个时刻（dueAt）， 但 taskToEntry 令 end = dueAt，周视图用 formatRange 画，于是它写着「15:30 – 15:30」。 模型里没有一个「点 / 区间」的区分，视图就只能猜。

本稿的承诺：改完之后，用户在任何界面都不需要、也不会被要求理解「任务 / 日程」。 没有开关、没有类型徽标、没有两个编辑器。捕获时不做类型选择；点开时不做类型判断。

核心原则：没有 kind 列。行为是时间形状的函数。

精度不落库，和今天 duePrecisionOf() 的选择一致（task.ts:22-28： 「persisting a second answer to the same question is how the two get out of sync」）。 下面每一条都能从四个字段算出来，不需要再存一个枚举。

这解释了旧代码里两个四分支 switch 为什么要存在。 isOverdue()（task.ts:80）和 reminderAnchorOf()（ReminderScheduler.ts:90）各自按四档精度分支， 根因是 due_at 被四种含义共用（截止时刻 / 捏造的午夜 / 半天桶 / 真区间）。 有了显式的区间之后，逾期判定塌缩成一条规则： 未完成且 now > end_at（全天档的 end_at 就是下一个本地午夜， 所以「次日起算逾期」自动成立）。提醒锚点还剩两个分支（全天 → 09:00 或半天桶小时； 其余 → start_at），因为「什么时候该打扰你」本来就是另一个问题，不该混进存储。
  • 为什么 end_at 可以等于 start_at，而不是「只有区间」。 今天一个 15:30 的截止任务在存储里只有一个时刻；强制补一个 30 分钟结束时间会改写用户的语义 （「交报告」不是一个 30 分钟的会）。让 end = start 表达「点」，既保留了旧语义， 又让视图能正确只写一个时刻——顺手修掉「15:30 – 15:30」。
  • 为什么不是「区间永远为真、没有空」。「这周有空就做」没有开始时刻；给它编一个 「周一 00:00」就等于替用户做了一个他没做的决定。NULL 是诚实的，而且 taskToEntry 的 null 分支已经把「不上日历」这件事说清楚了。
  • 为什么 list_id 保持可空。现有 events.list_id 就是可空的 （ON DELETE SET NULL）。迁移时替 13 条日程挑一个清单，是把它们搬进用户没选过的地方。 可空 + 详情面板显示「无清单」是唯一不撒谎的处理。

一处必须明说的后续工作量：现在的月视图只按 startAt 的本地日分桶 （MonthView.tsx:53、WeekView.tsx:144），所以跨多天的条目今天只显示在 第一天。模型允许 span 只代表视图必须会画它。全天线（周 / 多日 / 日视图都有）是最自然的落点： 一条横条跨过它覆盖的列。演示数据里 12 条日程全部当天起止，所以迁移当下不会看到回归； 但用户自己建过跨天日程的话，这是模型开放出来的新能力，不是迁移修好的旧账。

  • 点与区间的区别只在 end_at。没有第二种类型、没有布尔开关， 所以用户永远不需要选「这是截止还是会议」。他填不填结束时间，模型就知道。
  • 六档的格子没有变密。「不限 / 某天 / 某半天 / 某时刻 / 某段 / 跨天」是同一根轴上 逐渐增加的信息量，不是六个平行的类别。这正是用户说的「有的是明确时间，有的只是大概」。

04 捕获条 · 第一个控件从「选类型」变成「说时间」 同一根条，删掉了开关

现状 · 先问一个用户没有答案的问题

第一行是类型开关（QuickEventComposer.tsx:472-483）。 翻到「日程」时标题占位文案变成「要安排什么？」，底下的控件整套换掉。
  • 用户为了记一条「周五前把合同发给法务」，要先回答：它算任务还是日程？ 这个问题没有正确答案，因为两者在界面上没有区别（第 01 节）。
  • 翻错之后，标题、象限、时间全部换一套控件；G 稿的解法是「保留但收起」， 那是在承认这个开关本身有问题。

本稿 · 标题第一，时间第二

第一行是标题，第一个控件是时间。默认「不限」——不选也能直接回车添加。 时间行的六个 chip 是同一根轴上的递进，不是六个类别。

为什么时间是第一个控件，而象限不是。「什么时候」是捕获时已经在脑子里的东西 （用户说「有的是有明确时间」），不问也得问；「重要还是紧急」是事后判断，且它有一张常驻的板 可以随时改。所以捕获条把时间放在第一行、象限放在第三行，默认落在 Q4——与 TaskService.createInbox 的默认值一致。
捕获入口标题默认时间为什么
四象限板 · Ctrl+N空不限板是「重要 × 紧急」的镜头，不预设时间。
日历空槽点击空点中的那一天 / 那个时刻点哪儿就落哪儿，用户已经用位置回答了「什么时候」。
顶栏「新建」空今天没有上下文，给一个最容易改的默认。

四个入口，没有一个问类型。默认时间由入口上下文推出，用户只在自己想改的时候才碰它。

  • 「任务 / 日程」开关删除，不是隐藏。CaptureMode 类型、mode 属性、 type-seg 这一组控件一起消失。留一个隐藏的开关，等于留一个以后会被重新打开的洞。
  • 时间行的措辞是用户的原话。「不限 / 今天 / 明天 / 这周」——没有一个词需要解释； 第五个 chip 直接写「周四 15:00」，是结果而不是「自定义时间」这种抽象说法。
  • 第二层只在需要时出现。选了「今天」才出现「上午 / 下午 / 晚上 / 具体时间」； 选了「具体时间」才出现时钟与时长。这与详情面板已有的「时间精度」是同一套词 （task.json 的 detail.precision.*），不是新词汇。
  • 主按钮只有一个动词：添加。今天任务的动词是「添加」、日程是「新建」——那套分工是为两种 对象准备的。对象合并后保留「添加」，顶栏按钮改成不带宾语的「新建」。

06 重复 · 一个会也能「每周五」 规则挂在事项上，不挂在类型上

今天只有 tasks 有 recurrence 列，日程没有。合并之后， 「每周五复盘」是一个事项、一条重复规则，而不是「一个任务 + 十二个日程」。 但重复并不是对每一档都成立——因为它需要一个可以往前推的锚点。

精度档能重复？下一次怎么算理由
不限不下发规则（保留列）— 没有日期就没有下一次。现有 TaskService 的行为就是「无日期的任务只是完成」， 本稿不改：列在，规则永远不触发。
某一天能日期 + 一个周期同今天。
某半天能日期 + 周期，due_period 不变同今天。
某个时刻 / 某段时间能日期 + 周期，时钟与时长不变 这是新增能力。周会的下一次仍是同一时刻、同样的时长—— 「时长」由 end_at − start_at 推出，不用另存。
一段时间（跨多天，含「这周」）不能— 见下。
为什么跨天的不能重复（包括「这周」）：重复引擎只推一个锚点，其余信息由锚点派生。 一个 span 有两个端点，推的时候必须让端点保持同样的跨度；更要命的是，「每周一次、每次三天的出差」 的两次发生会重叠，而完成一条重复事项会派生下一条——重叠时「我完成的是哪一次」没有答案。 这是重复引擎的问题，不是模型的问题：模型已经能存它，只是重复按钮对 span 不出现。 「这周」是 span，所以同理。

完成时仍是「拆开」，不是「原地推进」。

沿用 TaskService.toggleDone 现有的决定（task-service.ts:100-125）： 当前这一条原地标成 done，同时新开一条下一次。理由是完成控件必须能画出一个勾—— 旧做法（在同一行上把日期往前推、留成 open）让勾永远打不上，一次点击和一次无声的空操作无法区分。 合并之后这个规则对会也成立：上周的周会显示成已完成，本周的周会是一条新的 open 事项。 这不是重复存储，是两段历史，而它们本来就是两段历史。

  • 重复是事项的属性，不是「任务」的属性。这一条单独就足以说明为什么不能维持两张表： 两张表里无论如何都得把 recurrence 复制一份到 events，然后两套推进代码要保持一致。
  • 「不能重复」是能力边界，不是类型。界面隐藏重复控件，是因为这个形状没有定义「下一次」， 不是因为它是另一类东西。用户不会被告知「日程不可以重复」。

日程 → 事项的默认值（三条规则）：
1. important = 0, urgent = 0, recurrence = NULL, due_period = NULL——不猜。 这会把每一场会默认放进「不重要不紧急」的象限，与今天新建任务的默认一致（createInbox）。
2. end_at <= now 的（已经开完的）→ status = 'done'， completed_at = end_at。这是本稿唯一替用户下的判断，理由见第 05 节。
3. end_at > now 的（未来的）→ status = 'open'。

18 条任务 → 18 条事项，逐档核对： 5 条不限（start/end = NULL）、8 条某天（全天区间）、2 条某半天 （全天区间 + due_period）、3 条某时刻（end = start）。 其中 2 条已逾期——它们仍然是 open，逾期判定与今天完全一致。 13 条日程 → 13 条事项，全部是「某段时间」（all_day = 0, end > start）； 其中已经结束的按规则 2 记成 done，未来的保持 open。

代价一：每一场会都成了「不重要不紧急」。四象限板现在会显示 13 条会议，全部堆在 Q4。它们有日期，会按日期排序，但当用户打开默认视图时，看到的确实是 一屏新的东西。缓解办法是演示/种子数据从现在起给日程也分配象限，让 Q4 不显得是一个垃圾桶； 但用户自己那 13 条不会因此被挪走——应用不替用户判断重要性。

代价二：清单删除守卫的口径变了。今天 ListService.remove 只数 tasks（list-service.ts:54-59）， 只有日程的清单是能删的，删完日程变成 list_id = NULL。合并后一类只有一张表， 守卫自然会数到会议：一个只剩会议的清单，现在删不掉了。 这更安全（不会悄悄孤儿化），但确实是一个用户能注意到的行为变化，必须在更新说明里写出来。

代价三：导出与备份的文案与列。CSV 现在只有任务列 （export-import.ts:169），合并后要么导出全部事项（需要加「开始 / 结束」两列）， 要么保持只导任务——但「只导任务」在新模型下没有定义。本稿选前者； 备份 JSON 的 BACKUP_VERSION 从 3 升到 4，旧文件照常能导入（缺字段按默认值）。

安全网（这是本稿要求实现方必须加的东西，不是可选项）

  • 迁移前写一份 JSON 备份。复用 BackupFile 序列化器，把当前库写成 pre-v4-backup.json 放在应用数据目录，并显示路径。今天没有任何自动备份； 一次不可逆的表替换不应该没有这张底牌。
  • 迁移必须可重入。migrate()（schema.ts）逐条执行语句、 没有包事务。所以：建新表 → INSERT OR IGNORE ... SELECT（按 id 幂等）→ 核对行数 → 才删旧表。中途崩掉，下次启动重跑不会重复插入，也不会丢掉一半。
  • 不要在迁移里删旧表之前忘了核对。行数不等就停在旧库上、把错误写进日志， 不要把数据删掉。宁可这次启动失败。
  • 方向是对的，风险在「不可逆」。见第 11 节——本稿最不舒服的一点不是映射， 是升级之后回不去。
  • 保留原 id 前缀。task_ / event_ 不重写：它们是日志与备份里的 线索，重写只会制造一次无意义的全表更新。前缀不是类型，id 仍然是不透明句柄。

为什么不叫「事项」（以及为什么不叫「待办」「事」）

  • 事项是对的模型名、错的界面词。它中性、覆盖两边，但它是公文语， 且要替换中文词表里 50 处「任务」、外加英文的 Task。换来的清晰度与「保留任务」相同—— 因为问题的根源是两个词，不是这个词选得不好。把「事项」写进 ADR 和本稿， 让它在代码与文档里当模型名；用户看不到它。
  • 待办把「还没做」写进了名词。一场开完的会不是「待办」，而合并后的每一项都能 完成、都可能已完成——名词和状态会互相打架。
  • 事太虚，做不了按钮文案（「添加事」不成话）。
  • 可逆性：如果以后确实想换成中性名词，「事项」是现成的落点——「待办事项」「日程事项」 在中文里都成立，所以这一步可以晚点再走，不必和这次模型合并绑在一起。
英文词表同步（同一张表的原则）：New event → New； Event / Task 的类型标签删除；Agenda 保留为视图名。 不需要新造一个 Item 去替换 Task——用户读到的仍然是 Task， 只是不再有一个 Event 在旁边让他比较。

11 最不舒服的三件事 说清楚，而不是藏起来

1 · 升级之后回不去（最不舒服的一条）。 migrate() 只执行版本号更高的迁移；一个旧版本的程序打开 v+1 的库时， 会跳过所有迁移，然后去查已经删掉的 tasks 表——启动即失败。 自动更新回滚、或用户重装旧安装包，都会走到这里。本稿的两条缓解： 迁移前写 JSON 备份（可被新版本重新导入），以及不删旧表、只把它标记为废弃 （代价是库里有冗余数据，收益是旧版本仍能读）。两条可以只选一条； 我倾向「先不删，过两个版本再删」，因为回滚窗口是真实的。
2 · 「过去的会按已完成导入」是一个语义赌注。 如果用户那天没去开会、但会后还要补一份纪要，这条会被记成 done。 它一次点击就能改回来，而且「已完成」在日历上只是安静地退后，不是划掉一整个时代。 但它仍然是应用替用户下的判断。替代方案（全部留成 open）会让升级后的第一屏变成 「逾期 15 条」——那个更糟。
3 · 清单删除守卫变严了。 一个只剩会议的清单，今天能删（会议变成 NULL 列表），合并后会被拒绝并显示条数。 这更安全，但它是一个用户可感知的规则变化，必须写进更新说明，否则会被当成 bug。
还有一件不是风险、但要排期的事：跨多天的条目在月 / 周视图里目前只画在第一天 （MonthView.tsx:53、WeekView.tsx:144）。模型允许 span 之后， 「画成一条横跨的带」是必须补上的渲染工作。它不影响这次迁移的正确性 （现有 13 条日程都是当天起止），但它决定「这周」在日历上看起来是否可信。

最后，正面回答用户的第二个问题：「产品设计一定要逻辑全局一致」。

这次合并之所以是对的做法，不是因为它「更优雅」，而是因为一致性有可检验的标准： 同一个对象在每一个镜头里都是同一个对象，且用户不需要先分类才能操作它。 现在四象限、清单、日历对「任务」是三种说法（有的能上日历、有的不能），对「日程」是另一种说法； 合并之后只有一种。捕获、点开、完成、重复、删除、备份——六个动作里没有一步会问 「这是任务还是日程」。这就是那句话在数据模型里的样子。

  • 本稿是设计提案，不是迁移方案。没有改任何 .tsx / .ts； 字段表与默认规则是给实现方的契约，不是已经落地的代码。
  • 可检验的验收：全仓 grep source === 'event' 应为 0； grep 用户词汇 新建日程 应为 0；两个编辑器类组件应只剩一个； items 表不存在任何叫 kind / type 的列。
