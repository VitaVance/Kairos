矩阵成为全局性质 · 设计稿 I

「产品设计一定要逻辑全局一致，这本质上是管理学的问题」
「艾森豪威尔矩阵的体现」
「任务 / 日程，你引入了这两个概念，但是在四象限和各个日历视图里完全区分不出来啊」
「我觉得不要让用户去理解 任务 / 日程 的区别」「别硬造概念，都是要干的事」

这个产品现在有三套逻辑同时在跑，而没有任何一条规则让它们对齐。 象限说「紧急」是一个用户的布尔值；时钟说「紧急」是截止时间；记录类型说 「这条事是任务还是日程」。三者从不互相看，所以它们在同一个界面上说出互相矛盾的话。 本稿把它们收敛成一套：一个对象、一个时钟、一个人填的字段。

02 核心决定 · 「紧急」用户说了算，但时钟会自己把它推上来 整份稿子的支点 · v2 依据用户裁定改写

v1 的立场已被推翻。本稿最初主张「紧急完全由时钟派生」，理由是 「我声明它紧急但它没有期限」等于「它很重要」，手标紧急只是重要性的重复输入。 用户否决了这一条，原话：

我觉得以用户为准，另外当有日程逐渐临近，则逐渐过渡到紧急。 这两句话合起来是一条双向规则：用户永远能说「它紧急」；而一个期限会自己把条目往紧急推。
三条路。v1 走的是第三条，被否了；本稿现在走第一条与第二条的组合。
　只有用户（H/J 稿）只有时钟（I 稿 v1）两者都要 · 本稿 v2
谁能改紧急 只有用户 只有时钟 用户能升高，不能压低；时钟按期限自动升高
无日期的急事 可以标紧急 永远不紧急，只能落 Q2/Q4 可以标紧急（用户说了算）
明天到期、用户说不急 听用户的，矩阵与时钟打架 进 Q1 进 Q1。想让它不急，就把日期推远——那是一个真实的决定，不是覆盖
「逐渐」体现在哪 无 无（48h 硬阈值一刀切） 五级读数，每级有自己的日期措辞与颜色，见下
紧急 ≡ 用户标了紧急 或 期限已把条目推到 urgent 级。
两句话，两个写入者，没有仲裁——因为它们不会给出相反答案：一个是布尔，一个是读数， 取「或」即可。§01 的那个矛盾之所以存在，是因为两个都叫「紧急」且都能被写成 1/0； 现在只有一个能被写成 1/0。

一处必须请你裁定： 按上表，near（不到 24 小时）还不进 Q1，要等过期才进。 也就是说「明天下午的事」在矩阵里仍是「重要不紧急」，「今晚 11 点的事」也是，直到它变红。 如果「逐渐过渡」只体现在颜色上而矩阵归属不动，用户在板上看到的仍是突变—— 某一刻它忽然从 Q2 跳到 Q1。 另一种做法是 near 就进 Q1（24 小时内 = 紧急），代价是 Q1 会长期拥挤， 而艾森豪威尔的本意恰恰是让 Q1 保持小。 本稿倾向后者不动（只有过期才进 Q1），但这是产品判断，不由设计稿决定。

用户压低时钟？不允许。 一条明天到期的事，用户说「不急」——界面不接受这个输入。想让它不急， 唯一的路是把日期推远，而推远是一个会留下痕迹的决定。 这条规则消灭了 v1 想消灭的那个矛盾，同时又没有夺走用户对无日期事项的控制权。

阈值是阶梯，不是渐变。五级之间有硬边界（14 天 / 3 天 / 24 小时 / 过期）。 但脚本已验证：相邻一小时的移动最多跨一级，所以用户看到的是一次小幅变化，不是一个悬崖。 「逐渐」在感知上成立，是因为措辞和颜色在四级里连续变化，而不是因为阈值被抹平。 真做成连续插值的话，同一条事在两次刷新之间会有肉眼可见的颜色漂移，那更像 bug 而不是信号。

  • 这消灭的是 §01 的第 1 条与第 4 条。「紧急」只剩一个可写入口（用户的布尔）， 时钟那边是只读读数。moveToQuadrant() 只翻 important； schedule() 写日期，读数随之变化——两条写入路径不再各写一个同名的数。
  • 数据迁移比 v1 简单：urgent 列保留并继续生效，旧数据里 urgent:true 的条目行为不变。v1 那处「老用户会发现东西变了」的风险消失了。
  • 板上的拖拽不再是单向。横轴（重要）与纵轴（紧急）都能拖；往 Q1 拖就是直接标紧急， 不需要先给它一个期限。这是 v2 相对 v1 更省事的一处。
  • 副作用：用户可以标一条「紧急」但完全没有日期，而时钟不会把它降下来。这是有意的—— 用户的话优先。但它意味着「Q1 里可能有永远不消失的条目」，需要 §06 里一条「清理」规则。

03 一个对象 · 「任务 / 日程」其实是时间精度 用户：「都是要干的事」

事实：这个应用在渲染层早就是「一个对象」了。 CalendarEntry（types.ts）把任务和日程投影成同一个形状，日历从不需要知道来源 （注释原话：「so the calendar never needs to know which source an entry came from」）。 分裂只在领域模型和用户词汇里，不在画面上。 Task 已经有 duePrecisionOf() → none | day | period | time。 「日程」不过是 precision = time 的那一条。

同一条「事」，四种时间精度。没有一种是另一种之外的东西。
用户说法今天的模型本稿的模型（一个 Item）板上日历上
整理书签Task，无日期dueAt: null在不在（没有位置）
周五前交Task，daydueDate，precision: day在在，全天条
上午写周报Task，perioddueDate + duePeriod在在，上午格
今天 18:00 发周报Task，timedueAt，precision: time在在，时刻格
产品评审CalendarEvent（另一个表）startAt + endAt，同样是 precision: time 的一条不在在，一个块
收敛 只剩一个对象：一条要干的事，可能带一个时间，时间可以是「某天 / 半天 / 准确时段」。 会议 = 带准确时段、并且通常有结束时间的那一条。它不需要第二个概念，也不需要第二个表。

为什么不是「给日程加上象限字段」：那会得到两个表、两套生命周期、 两个「完成」的语义（日程能不能标记为已完成？），然后用户仍然要选。用户的原话是 「不要让用户去理解任务 / 日程的区别」。加字段满足不了这句话，合并概念才满足得了。

生命周期的代价，必须承认：会议现在可以被勾掉（开完了）。 这是增强，不是退化——它让「这周开了哪些会」和「这周干了哪些事」用同一种方式统计。 但日程当前没有 status，合并意味着迁移时所有旧事件都要补一个 status: 'open'， 而旧日程的「完成」一旦出现，日历就得决定已完成的块画不画（建议：画，用 --tl-block-tint-muted，与已完成任务同一条规则）。

  • 一个概念，一个表，一个生命周期。不是「两个存储一个界面」——那是把不一致藏进适配层。
  • 「时间不确定性」是这个概念自带的维度，不是用来区分物种的。
  • 板是全集：所有未完成的事，包括开会。日历是有时间的那部分的全集。 两个投影，一个集合——这直接回答了「在四象限和各个日历视图里完全区分不出来」： 不需要区分，因为它们是同一种东西，变的只是「有没有一个准确时刻」，而那在两个界面都看得见。

03b 板是首页，所以板上必须有不带时间的事 一个真正要回答的产品问题

问题：有了一个对象之后，四象限板上要不要显示「今天 15:00 产品评审」这种有准确时刻的事？ 如果显示，板就成了日历的另一种排法；如果不显示，Q1 里永远只有「截止到期的事」，而开会这条最典型的 Q1 又缺席了。

三条路。选 B，理由在下面。
　A · 板只显示无时刻的事B · 板显示全部（本稿）C · 板按时间分两个区
「开会」在哪只在日历板上，Q1板的「有时刻」区
Q1 的含义「紧急」= 只有截止的事「紧急」= 现在就得处理，含马上要开的会被拆成两种紧急性
首页能否回答「现在该干什么」不能，要先切日历能能，但要多读一个分区
代价概念统一了，但矩阵仍然漏掉一半的承诺板上会有时间信息的 meta，密度上升又造了一个「区」，回到两个概念

选 B，而且「全部」是有定义的： 板 = 所有未完成的事，按重要 × 紧急分组。有准确时刻的那些在行尾显示时刻（「今天 15:00」）， 没有的显示日期或「无日期」。板不按时间排序——排序的是象限，不是时钟。 日历仍然是唯一能看见「时间如何排布」的地方，因为它是唯一有坐标轴的界面。

为什么这不会让板变成第二个日历：板的分组维度是重要 × 紧急， 日历的分组维度是时间位置。同一批事，两种问法。一个会议在板上回答「它有多要紧」， 在日历上回答「它占哪个格子」。两个问题不同，所以两个界面不重复。

代价 板上会出现同一时刻的多个条目（三个 9:00 的会），而板不作为时间冲突的检测器。 明确写进设计：冲突检测只在日历做。否则板会慢慢长成一个更差的日历。
  • 这条决定了本稿是「矩阵成为全局性质」还是「矩阵只是另一个视图」。若板排除有时刻的事， 它就只是一个「待办清单的另一种画法」，而用户抱怨的正是「各个视图里完全区分不出来」。
  • 密度问题有解：板上行尾的 meta 已经是「今天 / 无日期」，加时刻只是多两三个字符， 且可以用 --tl-text-tertiary 压下去。四列板每列本来就只显示有限条（现有 RECENT_COMPLETED_LIMIT 同级的截断）。

全天圆点 （退休）5px本稿删除。它自己的注释已承认是冗余信号，且四个界面早已 display:none。它与新标记是竞争关系，只留一个。

为什么是流内元素而不是绝对定位的角标：角标会和时间标签抢右端，而时间在窄 chip 上本来就要被容器查询裁掉。 放在首位则与竖条相邻、与标题同一条基线，不引入任何新的定位上下文，容器查询的行为完全不变。

代价：每个带标记的 chip 少 15px 标题宽（7px 标记 + 8px 间距）。 在月视图 118px 的 chip 上这是 13%。接受它，因为省下的这一比特无法从别处得到； 而不重要的 chip 一个像素都不付。

  • 两个通道，各管一摊：清单色 = 属于哪一摊事（用户可以自己命名与配色）；象限标记 = 这摊事有多要紧。 §2.4 说象限词汇「在任何地方都表示重要/紧急」——本稿用它就是这个意思，不是「第九个清单色」。
  • 填充不换。如果一个 chip 用象限色做底，用户就失去了「这是哪个清单」的信息， 而清单色是他自己选的。抢填充是最差的选择。
  • 时间与标记的冲突已解：时间在右端且可隐藏，标记在左端且永不隐藏。两者不在同一个轴线上竞争。
  • 放右边为什么不行（试过）：右端本来就是时间标签的地盘，且时间在 118px 以下要整段隐藏。 把标记放到右端，窄 chip 上它要么被一起裁掉，要么把时间挤成一个破折号。左端始终有空位——竖条之后就是标题。
  • 圆点 vs 方圆，试过四种：（a）7px 圆点、gap 5px：与清单色竖条贴得太近，橙清单 + 橙标记会糊在一起； （b）7px 圆点、gap 8px：分得开，但和 chip 原有的 5px 全天圆点在同一行读起来像两个意义相同的点； （c）9px 圆点 + 1.5px surface 边：最清楚，但多了一个「描边」语言，与 §3 的 block 语言不共享词汇； （d）7px 圆角 1.5px 的方圆、gap 8px——选它。形状和「点」不同，尺寸不变，不需要新令牌， 并且允许把那个冗余的全天圆点直接退休，一个 chip 只剩一个点。

06 两个时钟的治理规则 · 一句话，全应用执行 合并对象之后，这是唯一还会打架的地方

重要由你定，紧急由时钟定；象限是时钟的读数而不是你的输入，所以二者不可能不一致—— 当时间推着一条事跨过界线，界面把那一次移动说出来，而不是悄悄移动。

这一句同时规定了三件事，每一件都能被实现直接检查：

情形界面说什么界面不做什么
用户拖一条到 Q1/Q3「要给一个期限」+ 一键「设为今天」；若已有期限，直接移动。不静默修改 urgent（它已经不存在）。
期限把一条推进 48h 内那一次移动在卡头说一次：「移入 重要且紧急 · 明天到期」。不逐条弹 toast；不在每次刷新时重说。
期限过了日期标签转成逾期读数（「已逾期 2 小时」），象限读 Q1。不把逾期画成一个新的颜色家族——它还是 --tl-danger 语义，不是象限语义。
没有期限「无日期 = 不紧急」，它落在 Q2 或 Q4，界面照实说。不猜用户的意图，也不给一个「手动紧急」的后门。
失败模式 「无声降级」：一条用户觉得「急着要」的事，因为没有期限，被系统降到 Q4， 而界面没有任何一句话解释为什么。 补救：Q4 的空态与详情面板的截止字段必须写明「没有截止时间 = 不紧急」，并把「设为今天」放在旁边。 只要这一句在，降级就不是无声的。

用色规则（防第四套词汇）：「紧急」在文字里是一个词，用 --tl-text-secondary 或 --tl-text 印刷；它不配一个色块。 颜色只属于标记（qN-ink）。这样「紧急」不会长出第五种红。

  • 为什么这是「治理规则」而不是「显示规则」：它约束的是谁可以写什么——只有时钟能改变紧急， 只有人能改变重要。任何界面只要遵守这一句，就不可能再造出 §01 的矛盾。
  • 一句话版本给实现看：urgent 不是字段，是 urgencyOf(item, now)； 写路径只有 setImportant() 和 schedule()，没有第三个。
  • 失败模式的名字值得记住：「无声降级」是本稿唯一会主动让用户意外的地方， 所以它也是验收清单上的第一条。

07 捕获条 · 类型开关取消，时间开关接管 推翻 G 稿的那一半

G 稿 · 先分类，再记事 要求用户选

收集箱 添加

四个 chip 里有两个是用户无法诚实地填的：选「重要但紧急」却不给日期， 就是在造一条 §01 那样的矛盾。

本稿 · 一个开关 + 一个时间，紧急是读数 不要求用户分类

今天 18:00 到期 · 紧急
收集箱 添加

没有「任务 / 日程」。用户只回答两个真问题：重要吗？什么时候要？ 第三个问题（它是任务还是日程）由第二个答案推出来，不问。

  • 时间开关就是用户一直在选的那个开关。G 的「任务 / 日程」翻译成「无日期 / 有日期」， 而「有日期」再细分成天、半天、时刻——这些本来就是同一个连续的东西。
  • 紧急读数在输入时就更新。选「今天」立刻显示「紧急」，选「明天」也是（48h 内），选「无」显示「不紧急」。 用户在打字的时候就学会了这条规则，而不是之后被它惊讶。
  • 重要开关的选中态用 q2 系（q2-i 字 + q2-t 底）：重要但不紧急是这个开关注定最常见的状态， 也是 Q2 这个名字的语义锚点。若实现认为这会让「重要」看起来像只属于 Q2，可退回 --accent-ink—— 但那样就失去了与板的联系。
  • 一个开关而不是四个 chip：因为它真的只有一个布尔。四个 chip 是在模拟一个已经不存在的四选一字段。

10 与同批稿子的分歧 · 需要用户拍的那一刀 H / J 保留手动紧急，本稿不保留

同批次里 H-time-precision.html 与 J-one-item-model.html 在「合并成一个对象」这件事上与本稿一致， 但两者都保留 urgent 作为可手填的列，象限仍由「重要 × 紧急」两个布尔推出。 本稿是唯一主张把紧急改为派生的一份。这不是措辞差别，是产品会不会再次自相矛盾的差别。

　H / J本稿（I）
urgent 列保留，可手填，默认 0删除（或保留但不读），紧急由截止时间派生
「重要不紧急」+ 今天到期仍然矛盾：板上不紧急，时钟今天到期不可能：象限就是时钟的读数
无日期但「急」能表达不能，只能表达为「重要」（§02）
板上拖入紧急列直接翻转布尔索要一个 48h 内的期限（§04 / §06）
与用户抱怨的关系解决了「任务/日程」，没解决「两个紧急」两件都解决，代价是不能再手点「紧急」
需要拍板 如果用户仍然想要「不给期限也能标紧急」，那么 §02 的决定必须撤， 同时 §06 的治理规则要退回成「两个时钟都显示、允许不一致」。 两件事不能同时要。
  • 这不是路线之争，是同一句话的两种读法：用户说「逻辑全局一致」。 H/J 的读法是「一个对象，但象限仍是用户意图的记账」；本稿的读法是「一个对象，且象限必须能被时钟验证」。
  • 本稿的立场：用户还说了「这本质上是管理学的问题」。管理学的四象限里，紧急天然来自期限； 没有期限的事可以重要，但不会「紧急」。所以派生的读法更贴原意。
