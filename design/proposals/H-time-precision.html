时间精度 · 一种东西，四种说法 v1

产品里只有一个东西。没有「任务」，没有「日程」，没有那个开关。 它和别的东西唯一的区别，是时间说到多细：不限 · 某天 · 几点 · 一段时间。 四个词，捕获条、行、日历、详情面板用的是同一套。

「任务 / 日程，你引入了这两个概念，但是在四象限和各个日历视图里完全区分不出来啊。 别硬造概念，都是要干的事。只是有的是有明确时间，有的只是有个大概时间甚至没有时间限制。 比如开会是明确时间，平时工作可能只会具体到天或者半天，有些任务比较大，只能说是这周 或者下个月这种，或者完全不做限制」

「我觉得不要让用户去理解 任务 / 日程 的区别」

依据：task-service.ts:47-51（四种 TaskSchedule）、task.ts:19 （DuePrecision 派生）、calendar.ts:52-71（无日期 → null）、 TaskDetailPanel.tsx:66-76（面板里已有第三套精度词）、 TaskListScreen.tsx:52-58（逾期/本周分组）、 docs/DESIGN-LANGUAGE.md §1–§3。

01 阶梯：四个词，五种形状 用户只学四个词，存储允许五种形状

不限 none

什么时候都行。不占日历、不逾期、不进任何日期视图。 它待在日历下方的「不限」栏和四象限里。

例：读《深度工作》

某天 day / period

一整天里做完就行。可以再往下说半句：上午 / 下午 / 晚上。 半天不是第五个词，是「某天」的细分。

例：交报销单 · 今天

几点 time (+ end)

有钟点。可选给一个结束时刻；不给就是「三点」，给就是「三点到四点」。 这是唯一会长在时间轴上的一档。

例：产品评审会 · 11/26 15:00–16:00

一段时间 span (new)

一个窗口，从哪天到哪天。预设：本周 / 下周 / 这个月 / 下个月， 也可以自己挑起止。这是唯一能表达「出差三天」的形状。

例：整理 Q4 数据 · 本周

用户的原话 → 哪一档。每个说法都有归属，没有一个落在缝里。
用户这么说哪一档存储形状为什么不放到别档
「开会 15:00，一小时」几点time + 结束 16:00放到某天会丢掉钟点，也就丢掉冲突检测
「平时工作，具体到天」某天（全天）day—
「具体到半天 / 上午」某天 + 上午period新造一个「半天」词，等于让用户多学一个词；它本来就是某天之内的一段
「出差三天」一段时间span 11/3–11/5现有四种都盖不住：全是 0 长或 1 天的点。见下注
「这周弄完」一段时间 · 本周span 11/23–11/29拆成单独一档「周」会给「窗口多长」存第二个答案
「下个月吧」一段时间 · 下个月span 12/1–12/31同上；月只是窗口宽度的另一个预设
「完全不做限制」不限none—
  • 为什么必须有第五种形状 span。 none / day / period / time 四个全是「点」：0 长，或恰好一天。 没有任何一个能说「11月3日到5日」。在只有一个东西的模型里， 这意味着一件跨三天的事只能在最后一天出现一次，中间两天日历上什么都没有。 日历是一等视图，所以这个洞必须补——补在形状上，不是补在词上： 用户说的「一段时间」本来就存在，产品只是终于能把它存下来。
  • 为什么只有四个词，而不是七个。这是本稿最刻意的一次减法。 七个词的版本（不限/某天/半天/几点/本周/本月/以后）逐条没过： 「半天」是某天的细分（用户不会说「这个活是半天的」而不说哪天）； 「本周/本月」是同一形状的两个预设宽度；「以后」的行为和不限完全一样。 四个词里每一个都对应一个不同的行为，没有一个是仪式的。
  • 枚举名不进 UI。none/day/period/time/span 是代码里的拼写， 界面上永远只出现 不限 / 某天 / 几点 / 一段时间。 现有的第三套词（面板里的 全天/上午/下午/晚上/具体时间）一并收编： 「全天」= 某天的默认子项，「具体时间」= 几点。

象限行的 meta 从「日期或清单名」变成「日期；没有日期就说不限」。 以前无日期时它显示清单名，于是「不限」在板上是看不见的—— 用户抱怨的第一句里，「区分不出来」有一半是这件事。

  • 一句话规则：某天及以上给日期，几点给钟点，一段时间给两端，不限给「不限」。 四种说法在行里占的是同一个 .row__meta 槽， 所以扫一列时它们互相比得出来，而不是各占一块。
  • 一段时间多一个形状信号（标题前那个双边竖记号）。 文字在不同语言里长短差很大，形状不会。它是行里唯一不写字就能看出的精度。
  • 逾期 = 加红，不是删掉。「上周 · 11/16–11/22」用的是 --tl-danger-ink（5.62–6.19:1），同时把窗口写出来—— 用户得看得出哪一周没做，否则「顺延」是个盲操作。
  • 「不限」用三级墨（4.65–5.03:1），比日期轻一档： 它不是一条时间信息，而是「这里没有时间信息」。用二级墨会让它读成一个日期。
  • 组头带一个「全部顺延」。这正是 §06 那个「不自动滚」决定的配套： 顺延要一次点击，而不是一次重打。

    · 钉在周一会说谎——「出差三天」看起来像周一开始、周二周三空着。 用户真正要的是「这三天别给我排别的事」，钉一天给不了这个信息。

  • 一条带只写一次标签。横带在它开始的那一周写标题和起止； 延续到下一周时只保留左侧一段无字的色带（.band--cont）。 月视图一周只有 7×18px 的带区，重复写标题会先把带区塞满。
  • 跨度超过一周怎么办。按周切片，每片独立圆角与竖条。 「出差 11/28–12/3」在月视图是第 5 周右半段 + 第 6 周左半段两截， 中间用不圆角连起来。不追求把一个 DOM 元素跨行绘制——那需要绝对定位 覆盖日期头，会和点击热区打架（月格单击进日视图、双击新建）。
  • 「不限」栏在网格外面。这是本稿对 taskToEntry() 返回 null 的回答：函数不改，日历多问一句。 给无日期的东西编一个格子，正是 endOfDay／duePrecisionOf 这一整套「不编造」在防的事；但让它在日历上完全消失，在只有一种东西的模型里 就是一个洞。栏在网格下方、与网格共宽，读起来是「这个月之外」， 不会被误读成属于某一天——也不会被误读成属于某一周。

05 捕获条：第一行不再是「任务 | 日程」 先写，再挑精度；挑的那个控件坐在底栏

现状要你先分类

重要且紧急 重要不紧急 不重要但紧急 不重要不紧急

两件事在打架：翻到日程，象限 chip 消失、时间 chip 出现； 翻到任务，反过来。而「任务」这一侧的 5 个精度选项 （全天/上午/下午/晚上/具体时间）要到详情面板里才出现。 捕获时被迫先答一个和「什么时候」无关的问题。

本稿先写，后说时间

捕获时没有类型开关。时间是一个可选 chip，默认「不限」； 清单在左，时间在右，都是底栏里同一级的小控件。 用户不回答时间也能回车——那正是「不限」。

日期 今天 · 11月26日 ›

今天一整天做完就行。下面这行是这一天之内的细分，不是新的精度。

一段时间的预设——四个按钮，写进同两个日期字段

起止 11月23日 → 11月29日 · 7 天

存的是两个日期，不是「本周」三个字。到了下周一它不会自己往前跳——见 §06。

几点的两种形态——结束时刻可选

时刻 15:00 → 不写结束

不写结束就是「三点」。写了才画成一个高度，才参与冲突检测。

  • 为什么要有一个 chip，而不是「什么都不放」。 最省事的版本是捕获条只有一行字，时间回头再说。它比开关快， 但不够快在一个地方：用户的原话里有一半是在捕获当时就知道精度的 （「开会是明确时间」）。让他在捕获时多花 0 次点击，就得在之后多花 3 次 （打开详情 → 找「时间精度」→ 选）。所以时间 chip 在场， 但它是可跳过的、默认「不限」的——按 Tab 走开，回车，就完事。
  • chip 和面板、和行用的是同一个组件、同一套词。 面板里现在有 5 个选项，捕获条现在有 2 个开关，行里有一套缩写——三处三套。 本稿全部收成 .rungs + .subs 两层： 上层四个词永远在，下层随所选那一档换内容。
  • 为什么「某天」下面还有一行，而「一段时间」下面也是一行。 第二行不是精度，是那一档的参数： 某天的参数是「一天之内的哪一段」，一段时间的参数是「窗口多宽」。 四个词的位置永远不变，第二行的内容跟着变——用户不需要重学布局。
  • 清单在左、时间在右，分开。它们回答的是两个问题 （「归哪」和「什么时候」），合在一个 chip 里会让其中一个看起来是另一个的属性。
  • 主按钮 disabled 时的墨是 --tl-text-secondary （4.46–7.91），不是 --tl-text-disabled（1.45–2.74， 在 sunken 上会消失成一个空槽）。与 G 稿同一处有意偏离，实现时并入 §8。
  • 比旧开关快在哪，用数说话： · 旧：先点「任务/日程」（1 次），若是日程还要设时间（2–3 次），若是任务想设精度 要进详情面板（打开 + 滚动 + 选，3 次以上）。
    · 新：直接打字 → 回车（0 次）。想设时间：点 chip（1 次）+ 点档（1 次），共 2 次。
    关键差别不在次数，在顺序：旧流程强制你先回答一个与「什么时候」无关的问题， 新流程让「时间」永远是可跳过的收尾。

摩擦是一次点击，不是一次重打。顺延保留同样的宽度（周 → 周，月 → 月）， 所以「下个月」不会因为过了 1 号就变成一个三十天的怪窗口。

  • 这是管理学决定，不是 UI 决定。软期限的价值在于「它会到」。 让它自动后移，等于取消软期限这个概念，只剩一个装饰性的标签。 Todoist 的「This week」会自动滚，代价是它被大量用户当作噪音关掉； Things 的「Someday」从不滚，因为它根本不承诺日期。本稿走后者： 承诺了就到期。
  • 为什么不干脆不存日期、只存「本周」这个枚举。 那样「本周」在每个月、每一年都一样，就没有「过了」这回事—— 但代价是：日历上摆不出横带（不知道是哪一周），冲突检测做不了， 排序做不了，提醒也定不了。软期限也需要落在日历上，否则它又变成隐形。
  • 重复 ≠ 顺延。「每周都要做的事」是重复（recurrence.ts， 日/周/月已经在跑）；「这周该做但没做」是逾期的事件，不是序列。 本稿不让「一段时间」参与重复，见 §07。
  • 月同理。「下个月」= 12/1–12/31。到了 1 月 1 日它变成「上月」并逾期； 顺延是「往后推一个整月」（1/1–1/31），不是「从今天起 30 天」。

07 冲突：一条东西能不能同时是两种精度 点是点，段是段，一格只能有一个形状

组合能存吗谁赢 / 怎么处理为什么
某天 + 上午/下午/晚上能 不冲突，后者是前者的细分 同一个形状（一天之内）。这正是 period 存在的理由。
某天 + 几点（例如「今天」且「15:00」）能 几点赢，某天是它的推论 15:00 已经蕴含了「今天」。存下来只有一个日期 + 一个时刻，不存两个断言。
半天 + 几点（「上午」+「10:00」）不能 选「几点」时清掉桶，并按桶推一个默认钟点 「上午十点」是同一个断言的两种写法；并存就会出现「10:00 但下午」的坏状态。 现有 TaskSchedule 的联合类型已经保证了这件事，捕获条沿用。
一段时间 + 几点不能 拒绝；给一个「拆成两条」 窗口是软的、跨天的；时刻是硬的、落在某一分钟的。两者不是同一个问题的两个答案， 是两个东西：一件大事（这周做完）+ 一个会（周四三点）。硬合并会让日历要么丢掉横带、 要么丢掉块。
一段时间 + 某天不能 拒绝；某天是宽度为 1 的窗口，选它就等于选「一段时间」里的单日预设 同一条轴上的一格宽和一格窄不能同时为真。UI 上是同一个控件里的两个选项， 结构上不可能同时选中。
一段时间 + 重复不能 拒绝；重复只接受「某天」和「几点」 重复的锚点是一个日期（每周三、每月 5 号），不是一段。给段做重复要回答 「下一段的长度从哪天算」，答案永远是「和上一段一样」——那就等于一条无限长的段， 每次都逾期。Recurrence 现有三种频率都是按日期锚的，这个限制本来就存在。
重复 + 几点能 按日期 + 时刻锚，每次生成一个新块 「每周三 10:00 站会」——现有 nextOccurrence 已经这么做了。
不限 + 任何其他不能 「不限」就是 none，不是「没有偏好」 如果它表示「没偏好」，它就是一个可以和外层覆盖字段共存的值； 那需要两层结构。本稿让它是一个值：选了就是没有时间。

拒绝长什么样——不是禁用，是给下一步

这条已经是几点（周四 15:00）。一段时间的窗口不能同时带一个时刻—— 要软期限，拆成两条：一条「这周完成」+ 一条「周四 15:00 的会」。

  • 为什么用「不可选」而不是「选了再报错」。这四个词是同一个单选组， 同时只能有一个为真。让「一段时间」在「几点」已选时不可点， 比让用户点完再弹一个错要少一步，也少一个坏状态。
  • 「拆成两条」不是敷衍。用户原话里「开会是明确时间，平时工作可能只会具体到天」 本来就是两件事。合并成一条是产品硬造的，拆分是把用户的说法还回去。
  • 不做的：同一对象上挂两个时间。见过「软截止 + 硬截止」的设计（如 due 与 defer 两个字段）。它解决的是「什么时候开始做」和 「什么时候必须做完」，不是「说到多细」。两者混在一起，会让用户面对 4×4 个组合。 本稿只回答后者。

短写法为什么是缩写而不是图标

行里只有约 90px 给时间，而「本周 · 11/23–11/29」放下就需要缩到 11px—— §4.2 明令不许。所以行里用「本周」，把两端留给悬停提示和详情面板。 但词没有变：还是「本周」，不是「W」也不是一条色带。

为什麼不写「截止」

某天、一段时间、几点都是做的时间，不是「最晚什么时候」。 「截止日期」这个说法会把整条轴读成 deadline，于是「这周」被读成 「周五之前必须交」。用户原话里没有一次说「截止」，说的是「这周弄完」。

英文为什么是 today / 3 PM / this week

全部走 Intl，不拼字串——现有 formatDueDate 已经这么做。 新增两条文案：span.thisWeek 与 span.range（{{start}}–{{end}}）， 其余复用 due.withPeriod、period.*、detail.hint.*。

13 被否掉的四个方案 记下来，免得下一轮再提一遍

方案为什么否
加一档「以后 / Someday」 行为和不限完全一样（不占日历、不逾期、不进日期视图）。两个行为相同的档， 在捕获时逼用户二选一，正是「硬造概念」。真要分开，那是清单的活—— 一个叫「以后」的清单就是 Someday。
「本周」「本月」拆成两档 两者是同一形状（span）的两个预设宽度。拆开就要为「窗口多长」存第二个答案， 而 duePrecisionOf 的全部意义就是不给同一个问题存两个答案。 拆开还会长出一张 3×3 的兼容矩阵（周+月+季）。
保留开关，只是把它挪到第二行 用户说的是「不要让用户去理解区别」，不是「别放在第一行」。 只要还有「任务/日程」这两个词，他就得先决定自己是哪一种—— 而捕获的那一刻恰恰是最不该做这个决定的时候。
不给「一段时间」单独形状，用「某天 + 一个跨天标记」 跨天标记要回答「到哪天为止」，那已经是一个第二日期字段了； 不如直接给两个日期。而且「某天 + 跨天到某天」在模型上就是一个区间， 多一个标记字段只是把区间拆成两个断言，又回到「同一条东西两个说法」的老问题。

最后一句留给时间轴本身：本稿没有动四象限、清单、重复、提醒、撤销。 它只做了一件事——把「时间说到多细」从三个互相打架的地方 （行、日历、面板）收成一个，并让它成为产品里唯一的分类轴。
